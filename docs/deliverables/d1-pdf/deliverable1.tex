\subsection{Stakeholder Problem \& Chosen Context}

Organizations frequently face operational bottlenecks, submission delays, and auditing errors in managing corporate expense reimbursements and purchase requests due to legacy reliance on paper routing and ad-hoc chat channels. This unmanaged process leads to three fundamental failure modes:\\
\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{No Request Visibility:} Requesters cannot track the status of their submissions, resulting in repeated inquiries, lost documentation, and unmanaged procurement pipelines.
  \item \textbf{No Audit Trail:} Organizations lack verifiable records of reviewer identities, decision timestamps, and justifications, making compliance tracking and retrospective audits impossible.
  \item \textbf{Unchecked Conflicts of Interest (Self-Approval Risk):} Reviewers or executives who submit requests can unilaterally approve their own requests (Self-Approval) in the absence of hard automated domain guards.
\end{enumerate}
This product is a dedicated \textbf{Workflow and Approval System} engineered to digitize corporate expense and procurement workflows with strict role boundaries: Requester, Reviewer, and Admin (Sprint 3).\\

\subsection{Product Scope \& Explicit Exclusions}

\subsubsection{In Scope (Whole Product Baseline)}
\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Request creation and lifecycle tracking (\texttt{PENDING}, \texttt{APPROVED}, \texttt{REJECTED})
  \item Reviewer task queue and decision workflow
  \item Automated reviewer assignment engine
  \item Immutable append-only approval history and audit trail
  \item Return for revision and resubmission workflow (Sprint 2)
  \item Multi-stage hierarchical approval workflow (Sprint 2)
  \item Document and receipt attachments with secure access control (Sprint 2)
  \item Search, filter, and aggregate expense reporting (Sprint 3)
  \item Administrative user account and assignment management (Sprint 3)
  \item Hardening, automated regression test suites, and containerized deployment (Docker/GCP)
\end{itemize}
\subsubsection{Sprint 1 Slice (Delivered in this Release)}
\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{F-01:} Authentication \& Session (Login/Logout/Current User with HTTP-only cookie)
  \item \textbf{F-02:} Request Creation (Validation, requestNo generation, reviewer assignment)
  \item \textbf{F-03:} My Requests \& Data Isolation (View personal requests with isolation guards)
  \item \textbf{F-04:} Review Queue \& Decision (Approve/Reject with comment, Self-Approval Guard, State Guard)
  \item \textbf{F-05:} Approval History write (Atomic append-only transaction logging)
\end{itemize}
\subsubsection{Explicit Exclusions (Sprint 1 Deferred Scope)}
\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Live payment gateway integration and automatic fund disbursement
  \item External notifications (SMS, Email, or Slack/Teams webhooks)
  \item Live banking system integrations
  \item Multi-currency support (exclusively supports Thai Baht - THB)
  \item Public self-registration or self-service password recovery (uses authenticated seed demo accounts)
  \item File and receipt attachments in Sprint 1 (deferred to Sprint 2)
  \item Return for revision workflow in Sprint 1 (deferred to Sprint 2)
  \item Multi-stage approval hierarchy in Sprint 1 (deferred to Sprint 2)
  \item Executive analytics dashboard in Sprint 1 (deferred to Sprint 3)
  \item Real PII or production secrets (all fixtures utilize synthetic mock data)
\end{itemize}

\textbf{BR-05} & \textbf{Reviewer Assignment:} Every request must have an assigned reviewer; only the designated assigned reviewer has authorization to execute decisions. & 403 \texttt{ACCESS\_\allowbreak DENIED} & S1 \\ \hline
\textbf{BR-06} & \textbf{Append-Only History:} Every state-changing action (submit/approve/reject) must append an immutable record to \texttt{ApprovalHistory}; modifications/deletions forbidden; status and history update atomically. & No update/delete endpoints; full database transaction rollback on error & S1 \\ \hline
\textbf{BR-07} & \textbf{Decision Validation:} Decision action must be either \texttt{APPROVE} or \texttt{REJECT}; \texttt{REJECT} requires a non-empty comment between 3--500 characters; \texttt{APPROVE} allows optional comment up to 500 characters. & 400 \texttt{VALIDATION\_\allowbreak ERROR} & S1 \\ \hline

\subsection{Purpose and Scope}

This document defines the system-level design for the Corporate Expense and Purchase Request approval system. It describes the architecture, data model, role and permission rules, UI structure, API conventions, authentication lifecycle, configuration, deployment approach, and security expectations.\\

Sprint 1 implements a working vertical slice:\\

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item authentication and session handling;
  \item request creation;
  \item requester-owned request tracking;
  \item reviewer assignment and review decisions;
  \item append-only approval history;
  \item backend enforcement of self-approval, state, validation, and access-control rules.
\end{itemize}
The design is intentionally a modular monolith. It does not use microservices, message queues, external caches, real payment integrations, or external notification services in Sprint 1.\\

  \item \texttt{REVIEWER} may create requests in Sprint 1 so that BR-01 no-self-approval can be tested with a real reviewer-owned request.
  \item \texttt{ADMIN} is present in the enum for future work only; it is not seeded and has no Sprint 1 endpoint.
\end{itemize}

\subsubsection{Review endpoint check order}

The backend must enforce checks in this order:\\

\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Authentication $\rightarrow$ \texttt{401 UNAUTHORIZED}.
  \item Role is \texttt{REVIEWER} $\rightarrow$ \texttt{403 FORBIDDEN}.
  \item Current user is not the request owner $\rightarrow$ \texttt{403 SELF\_APPROVAL\_NOT\_ALLOWED}.
  \item Current user is the assigned reviewer $\rightarrow$ \texttt{403 ACCESS\_DENIED}.
  \item Request status is \texttt{PENDING} $\rightarrow$ \texttt{400 INVALID\_STATE\_TRANSITION}.
  \item Decision payload is valid $\rightarrow$ \texttt{400 VALIDATION\_ERROR}.
\end{enumerate}
Checking self-approval before assignment ensures BR-01 is enforced even when the request is assigned to another reviewer.\\

\subsection{Authentication and Session Lifecycle}

\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{Login:} validate body, find user by email, compare with \texttt{bcrypt.compare}, sign a JWT \texttt{\{ sub, role, iat, exp \}} using \texttt{JWT\_SECRET}, set the \texttt{token} cookie, return the user without \texttt{passwordHash}.
  \item \textbf{Authenticated request:} read the cookie, verify signature and expiry, load the user, attach \texttt{req.user}. Missing/invalid/expired cookie $\rightarrow$ \texttt{401 UNAUTHORIZED}.
  \item \textbf{Authorization:} enforce role, ownership, assignment, and state in the order defined in section 4.3.
  \item \textbf{Current user:} \texttt{GET /api/auth/me} returns \texttt{\{ id, email, name, role \}} only.
  \item \textbf{Logout:} \texttt{POST /api/auth/logout} clears the cookie with \texttt{maxAge: 0}; the client redirects to \texttt{/login}.
  \item \textbf{Password handling:} bcrypt cost 12; hashes are never logged or returned; demo password is local-only.
\end{enumerate}

\subsection{Error Handling, Logging, and Security}

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item A central error\allowbreak{} handler maps validation and domain errors to the standard error shape.
  \item Prisma uses parameterized queries, reducing SQL injection risk.
  \item React escapes rendered text by default; avoid \texttt{dangerouslySetInnerHTML}.
  \item The JSON API plus \texttt{sameSite=lax} cookie reduces CSRF risk. Additional CSRF hardening is deferred.
  \item Rate limiting, audit export, and admin actions are Sprint 3 concerns.
  \item Logs must not contain passwords, tokens, secrets, or unnecessary personal data.
  \item Error responses must not reveal stack traces or internal implementation details in production.
\end{itemize}

\subsection{Feature SDS}

The system must support authenticated sessions for the requester and reviewer\\
slices:\\

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item verify email/password credentials against the \texttt{User} table;
  \item issue a signed JWT in an httpOnly cookie;
  \item load the current user for protected requests;
  \item expose login, logout, and current-user endpoints;
  \item reject missing, invalid, expired, or deleted-user sessions with \texttt{401};
  \item reject authenticated users who lack the required role with \texttt{403};
  \item never return or log \texttt{passwordHash}.
\end{itemize}
Authentication is stateless in Sprint 1. Logout clears the cookie on the client;\\
server-side token revocation is a documented limitation and is deferred.\\


\subsection{UI Specification}

\subsubsection{LoginPage}

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Fields: \texttt{email}, \texttt{password}.
  \item Inline validation for required fields and email format.
  \item Loading state while the request is in flight.
  \item Invalid credentials show the server error code/message.
  \item Successful login redirects according to the user's role.
  \item The client must not store the JWT in \texttt{localStorage}.
\end{itemize}
\subsubsection{Session behavior}

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Authenticated screens call \texttt{GET /api/auth/me} on load or use the login response.
  \item A \texttt{401} response clears client auth state and redirects to \texttt{/login}.
  \item The logout action calls \texttt{POST /api/auth/logout} and redirects to \texttt{/login}.
  \item Role-aware navigation is a UX aid, not an authorization boundary.
\end{itemize}

\subsubsection{Workflow \& Business Rules}
\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{Creation \& Validation (\texttt{F-02} / \texttt{BR-04}):}
\end{enumerate}
\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Validate request payload on the server using Zod (\texttt{.strict()}).
  \item \texttt{title}: trimmed string, 3–150 characters.
  \item \texttt{amount}: positive number > 0 and \texttt{<= 9,999,999,999.99} (stored as \texttt{Decimal(12,2)}).
  \item \texttt{category}: must be one of \texttt{EQUIPMENT | TRAVEL | SOFTWARE | SUPPLIES}.
  \item \texttt{description}: trimmed string, 1–1,000 characters.
  \item Invalid payloads return \texttt{400 VALIDATION\_ERROR} with field details and persist nothing.
\end{itemize}
\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{Request Number Generation (\texttt{D-10}):}
\end{enumerate}
\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item Server generates \texttt{requestNo} in format \texttt{REQ-YYYYMMDD-NNNN} (e.g. \texttt{REQ-20261111-0001}), retrying on unique-constraint collision.
\end{itemize}
\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{Deterministic Reviewer Assignment (\texttt{BR-05} / \texttt{D-03}):}
\end{enumerate}

\subsection{Feature SDS}

The reviewer slice lets a \texttt{REVIEWER} see only the \texttt{PENDING} requests assigned to them, inspect one request with its history, and record an \texttt{APPROVE} or \texttt{REJECT} decision with an optional/required comment. A decision changes the request status and appends an \texttt{ApprovalHistory} row inside one database transaction. The backend enforces every business rule; hiding UI controls is not authorization.\\

\subsubsection{Workflow and enforcement order}

\texttt{POST /api/requests/:id/review} checks are executed in this exact order:\\

\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \textbf{Authentication} - no/invalid \texttt{token} cookie $\rightarrow$ \texttt{401 UNAUTHORIZED}.
  \item \textbf{Role} - role other than \texttt{REVIEWER} $\rightarrow$ \texttt{403 FORBIDDEN}.
  \item \textbf{Existence} - unknown request id $\rightarrow$ \texttt{404 NOT\_FOUND}.
  \item \textbf{No self-approval (BR-01)} - \texttt{requesterId === currentUser.id} $\rightarrow$ \texttt{403 SELF\_APPROVAL\_NOT\_ALLOWED}.
  \item \textbf{Assignment (BR-05)} - \texttt{assignedReviewerId !== currentUser.id} $\rightarrow$ \texttt{403 ACCESS\_DENIED}.
  \item \textbf{State lifecycle (BR-02)} - status is not \texttt{PENDING} $\rightarrow$ \texttt{400 INVALID\_STATE\_TRANSITION}.
  \item \textbf{Decision payload (BR-07)} - invalid \texttt{decision}/\texttt{comment} $\rightarrow$ \texttt{400 VALIDATION\_ERROR}.
  \item \textbf{Commit} - status update + \texttt{ApprovalHistory} insert in one transaction (BR-06).
\end{enumerate}
Checking self-approval before assignment makes BR-01 testable even when the owner's request is assigned to another reviewer.\\

\subsubsection{Rules}

\begin{itemize}[leftmargin=*,itemsep=2pt,topsep=2pt]
  \item \texttt{GET /api/requests/pending} returns only requests where \texttt{assignedReviewerId = currentUser.id} and \texttt{status = PENDING}, oldest first (\texttt{createdAt ASC}).
  \item \texttt{APPROVE} sets \texttt{APPROVED}; \texttt{REJECT} sets \texttt{REJECTED}; no other transitions are allowed.
  \item \texttt{REJECT} requires a trimmed comment of 3-500 characters.
  \item \texttt{APPROVE} accepts no comment or a trimmed comment of at most 500 characters. Empty/whitespace-only comments are stored as \texttt{null}.
  \item The status update uses a conditional write (\texttt{where: \{ id, status: PENDING \}}); if the request was decided concurrently, the transaction fails with \texttt{INVALID\_STATE\_TRANSITION} and no history row is added.
  \item History rows are append-only. Sprint 1 exposes no update or delete history endpoint.
\end{itemize}
